# Инженерный процесс и подготовка к интервью

Игра даёт реальные задачи для практики. Для каждого занятия выбираем одну игровую цель и одну связанную инженерную тему. Обсуждаем решение, делаем небольшое изменение, проверяем результат и тренируем объяснение. Подготовка охватывает код, доставку изменений и ответственность за работающий продукт.

## Что изучаем на проекте

| Когда | Практика | Что сможем показать и объяснить |
| --- | --- | --- |
| Сейчас и первые игровые шаги | Задача с критериями готовности, ветка, diff, commit, PR, review | Почему изменение имеет такой объём; как прочитать историю и принять замечание |
| Сейчас и развитие механик | GitHub Actions: события, jobs/steps, runner, Node, lock-файл, cache, логи | Что проверяется на PR; как найти причину сбоя; почему зелёный CI не доказывает правильность игры |
| Физика и состояния игры | Vitest, граничные случаи, затем Playwright и подключение тестов к CI | Как выбрать уровень проверки и воспроизвести ошибку |
| Меню и завершённая комната | Доступность, адаптивность, состояния UI; практический разбор Tailwind | Как проверить клавиатурную навигацию и обосновать способ стилизации |
| После локального демо | Python/FastAPI, REST, схема данных, валидация, pytest, обработка ошибок в React | Контракт frontend/backend; доверие к данным клиента; диагностика неуспешного запроса |
| История и обновление результатов | SSE и жизненный цикл соединения; OIDC для аккаунта, авторизация доступа | Переподключение, завершение подписки, различие входа и прав доступа; границы доверия |
| Публикация демо и сервиса | Docker, GitHub Actions для выпуска, артефакты, настройки среды, secrets/permissions | Разница CI и CD; из какого коммита собрана версия; как проверить выпуск и вернуться к предыдущему |
| Работа опубликованного проекта | Логи, health check, диагностика сбоя, краткая инструкция восстановления | Как отличить ошибку UI, API и окружения; как подтвердить восстановление |

Темы не требуют установки всех инструментов сразу. Каждый инфраструктурный шаг выполняем вместе: сначала назначение и маленькое изменение, затем запуск и разбор результата. Вариант хостинга, облако и связанные расходы выбираем на этапе выпуска. Текущий workflow выполняет только lint и build.

## Codex как часть работы

Научиться ставить агенту ограниченную задачу, читать его изменения и проверять результат — отдельная цель. Фиксируем, что написал Кирилл, что подготовил Codex и какое решение было принято. Предложение агента проверяем по требованиям, diff и наблюдаемому поведению. Review тем же агентом не считаем независимой гарантией правильности.

Для задания Codex указываем цель, нужные файлы или ошибку, ограничения и критерий готовности. Устойчивые правила нашего учебного режима находятся в `AGENTS.md`. Эти приёмы описаны в [официальных рекомендациях OpenAI](https://learn.chatgpt.com/guides/best-practices).

Пример задания для текущего урока:

> Объясни текущий CI в `.github/workflows/ci.yml`. Свяжи каждый шаг с нашим package.json и успешным запуском в Actions. Файлы пока не меняй. В конце дай один вопрос на понимание и дождись моего ответа.

Пример для review своего изменения:

> Проверь diff моей ветки относительно main по критерию готовности урока. Для существенных проблем покажи файл, причину и способ воспроизведения. Не переписывай решение целиком: сначала дай подсказку. Отдельно укажи, какие проверки выполнены и чего они не покрывают.

Для рассказа на интервью собираем реальные примеры: постановка задачи агенту, найденная проблема, принятое или изменённое предложение и подтверждение результата. Не выдумываем отклонённые советы или выигрыш во времени. Пока у нас есть пример подготовки репозитория с Codex; собственные review и диагностику будем добавлять по мере выполнения.

## Урок 0.1 — существующий workflow

Открыть [ci.yml](../.github/workflows/ci.yml) и [первый успешный запуск](https://github.com/iamKiryl/elsa-game/actions/runs/37220648333).

| Часть нашего файла | Назначение |
| --- | --- |
| `name: CI` | Имя workflow в интерфейсе Actions |
| `on: push / pull_request` | Запуск при push в main и событиях PR, направленного в main; отдельный push в feature-ветку без PR не подходит |
| `permissions: contents: read` | Разрешение чтения содержимого репозитория для GITHUB_TOKEN этого workflow |
| `jobs: check` | Одна задача с последовательными шагами |
| `runs-on: ubuntu-latest` | Окружение GitHub, в котором выполняется задача |
| `timeout-minutes: 10` | Верхняя граница времени выполнения job |
| `actions/checkout` | Получение кода репозитория на runner |
| `actions/setup-node` | Подготовка Node из .nvmrc; параметр cache включает кэш npm |
| `npm ci` | Установка зависимостей по lock-файлу |
| `npm run lint` | Запуск ESLint согласно package.json |
| `npm run build` | Сначала TypeScript, затем production-сборка Vite |

Термины workflow, event, job, step и runner подробнее объяснены в [документации GitHub](https://docs.github.com/en/actions/get-started/understand-github-actions).

Практика на этот раз:

1. В запуске Actions открыть job `check` и найти шаг `npm run build`.
2. Найти в его логах две части сборки и сопоставить их со скриптом в package.json.
3. Своими словами объяснить, что уже доказал этот запуск и чего он пока не проверяет.

Первый вопрос для обсуждения: сработает ли текущий CI, если отправить commit в новую feature-ветку, но не открыть PR?

После ответа разберём ещё по одному вопросу: зачем npm ci, что делать при красном check, чем CI отличается от деплоя. Не требуется сразу знать ответы на все вопросы. Позже проведём небольшой учебный сбой в отдельной ветке и исправим его, не включая сломанное состояние в main.

## Свидетельства обучения

После занятия добавляем 3–5 строк в [LEARNING_LOG.md](LEARNING_LOG.md): ссылка на изменение или запуск, решение, вклад Codex, реальная проверка и то, что Кирилл смог объяснить. Запись «настроено» не означает «освоено». По этим примерам затем репетируем ответы на интервью, включая краткое объяснение по-английски.
