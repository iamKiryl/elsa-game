# Elsa — план разработки и обучения

## Формат работы

Кирилл пишет игровой код сам. Ассистент объясняет одну новую идею, предлагает небольшое задание, проверяет diff и помогает найти ошибку. Готовую реализацию целого урока даём только по явной просьбе. Каждый этап можно разбить на несколько коротких занятий.

Текущая основа: React 19, TypeScript, Vite и PixiJS 8. Сейчас приложение показывает заголовок. Механик и сцены ещё нет. Remotion — отдельный будущий проект.

## Что именно делаем

Первое демо — одна небольшая комната на один экран. Белый кролик Elsa ходит и прыгает по платформам, собирает три осколка звезды и достигает выхода. В конце можно начать заново. При падении за пределы комнаты кролик возвращается на старт.

Управление для демо: A/D или стрелки, Space для прыжка; кнопки старта и перезапуска доступны с клавиатуры. Сначала поддерживаем браузер на компьютере. Макет должен помещаться в окне; управление касаниями — отдельное возможное улучшение.

Визуальная идея: белый кролик с голубым глазом, тёмный фон и светящиеся осколки. Сначала используем один кадр существующего спрайт-листа Elsa, затем добавим анимации. Работаем с копией материала, установленного питомца не меняем. Размер картинки и физический прямоугольник столкновений задаём отдельно.

## Этапы

| Этап | Что появляется в игре | Что изучаем и обсуждаем на review |
| --- | --- | --- |
| 0. Основа | Репозиторий, план, lint/build в CI | working tree, staging, commit, branch, diff, зачем CI |
| 1. Сцена и Elsa | Одна сцена PixiJS и неподвижный кролик | React ref/effect, асинхронная загрузка, очистка ресурсов, координаты и текстуры |
| 2. Движение | A/D и стрелки, поворот, idle/run | события клавиатуры, время кадра, состояние игры вне React render |
| 3. Физика | Гравитация, прыжок, пол и платформы | скорость и положение, столкновения прямоугольников, чистые функции, Vitest |
| 4. Демо | Три предмета, счётчик, выход, победа и restart | состояния playing/won, обмен игры с React, доступность меню, Playwright |
| 5. Бой | Один враг, одна атака, здоровье и смерть | состояния персонажей, таймеры, предотвращение повторного урона |
| 6. Короткий забег | Три комнаты из готовых шаблонов, три вида улучшений | данные отдельно от логики, воспроизводимая случайность, сброс забега |
| 7. Завершение | Короткий сюжет, звук, финал и демо по ссылке | UX, документация, проверка производительности и выпуск версии |

Первый рубеж — этап 4. Этапы 5–7 начинаем после законченного демо и оценки того, интересно ли играть. Для расширения ориентир — забег на 3–5 минут; длительность проверяем игрой. Полную генерацию уровней, боссов, инвентарь, мультиплеер и постоянную прокачку пока откладываем.

## Как понимаем, что этап готов

- **Сцена:** один canvas; Elsa видна целиком; повторное монтирование в React StrictMode не оставляет лишние canvas, ticker или обработчики; ошибки загрузки не теряются.
- **Движение:** можно идти в обе стороны; отпускание клавиши и потеря фокуса останавливают движение; скорость задаётся в единицах в секунду.
- **Физика:** нельзя прыгать бесконечно в воздухе; приземление на платформу устойчиво; определено поведение при ударе сбоку/снизу и падении за экран. Отдельно проверяем несколько частот кадров и возвращение на вкладку после паузы.
- **Демо:** каждый предмет считается один раз; выход открывается после трёх предметов; перезапуск сбрасывает героя, предметы и счёт; комнату можно пройти от начала до конца несколько раз подряд.
- **Бой:** урон имеет понятный интервал; погибший враг перестаёт атаковать; смерть игрока переводит игру в отдельное состояние.
- **Забег:** улучшение влияет на конкретную характеристику; переходы между комнатами сохраняют состояние забега; новый забег его сбрасывает.

## Технические решения

Начинаем с обычного PixiJS внутри одного React-компонента. React отвечает за DOM-интерфейс, PixiJS — за canvas. Положение персонажа обновляется игровым циклом; React получает только нужные интерфейсу изменения, например счёт или победу. Не вызываем React setState на каждом кадре ради координат.

Разделяем код по мере появления ответственности: компонент сцены, ввод, состояние игры, физика и отрисовка. Сначала достаточно нескольких файлов; заранее не создаём собственный движок, ECS или сложную систему событий. Для прямоугольных платформ используем простую собственную физику; если требования перерастут её, отдельно обсудим физический движок.

TypeScript strict включён с начала. Новые библиотеки добавляем вместе с задачей, которую они решают. Для оформления первых экранов достаточно CSS; Tailwind можно разобрать на этапе меню как отдельный учебный шаг.

## Проверки

- Сейчас: ESLint и production build с проверкой типов, локально и в GitHub Actions.
- С физикой: Vitest для столкновений, приземления и разрешения прыжка. Проверяем граничные случаи, а не копируем реализацию в тесты.
- С состояниями игры: проверки однократного сбора предмета и полного restart.
- С демо: Playwright для запуска, видимых UI-состояний и перезапуска. Столкновения проверяем отдельно на уровне игровой логики; наличие canvas само по себе не доказывает, что игра работает.
- Визуал и ощущение управления проверяем вручную. Измерения производительности добавляем при наблюдаемой проблеме.

## После демо: необязательное fullstack-расширение

Если приоритет — подготовка к fullstack-интервью, этот блок можно пройти сразу после этапа 4, перед боем и расширением забегов.

Небольшой сервис на Python/FastAPI может хранить результаты забегов и отдавать их React-экрану истории. Это отдельный этап: контракт REST API, валидация на сервере, загрузка/ошибки в UI, база данных и pytest. Результаты, присланные клиентом, считаем недоверенными; серьёзная соревновательная таблица потребует отдельного решения для проверки забегов.

SSE имеет смысл, если появится экран с живым обновлением результатов. OIDC — если понадобятся аккаунты и личная история. Docker и деплой — когда будет готов сервис. Эти возможности не входят в обязательное первое демо.

## Ближайшее занятие: 1.1 — сцена

Ветка: `feat/01-game-scene`.

1. Создать `GameCanvas.tsx` в `src/game/` и подключить компонент в `App`.
2. Сначала добавить DOM-контейнер и типизированный ref. Объяснить, почему для ссылки на контейнер нужен ref.
3. После проверки этого шага создать и инициализировать PixiJS Application в effect, добавить его canvas в контейнер.
4. Разобрать асинхронный init и cleanup, включая размонтирование до окончания init. Оставить StrictMode включённым.
5. Проверить одну пустую сцену, отсутствие ошибок и корректное удаление сцены при размонтировании. Запустить lint/build и показать diff на review.

Коммит после проверки: `feat: add PixiJS game scene`.

Следующий небольшой шаг 1.2 — скопировать спрайт-лист Elsa в игровые assets, выбрать один кадр и показать кролика. Затем зафиксировать происхождение материала в README. Движение добавляем отдельным уроком.
