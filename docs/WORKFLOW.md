# Один урок — небольшое проверяемое изменение

Кирилл пишет код. Ассистент даёт задание и проводит review. Подготовка репозитория — отдельная стартовая работа; дальнейшие игровые изменения делаем постепенно.

## Цикл

1. Выбираем один видимый результат и критерий готовности из плана.
2. Создаём ветку от актуального `main`.
3. Пишем небольшую часть, запускаем приложение и объясняем результат своими словами.
4. Запускаем проверки, читаем diff и делаем review в чате. Ассистент указывает проблему и объясняет причину; исправление сначала пробует написать Кирилл.
5. Делаем осмысленный commit. Внутри одного урока может быть несколько коммитов, если у каждого понятная цель.
6. Отправляем ветку на GitHub и открываем PR: что изменилось, как проверено, какое решение важно обсудить. После review и успешного CI объединяем в `main`.

Для первого урока:

```sh
git switch main
git pull --ff-only
git switch -c feat/01-game-scene
```

Проверки перед коммитом:

```sh
npm run lint
npm run build
git status --short
git diff
git diff --check
```

`git diff` показывает изменения уже отслеживаемых файлов. Новые файлы видны в `git status`, а после `git add` — в `git diff --cached`. Добавляй только файлы своего изменения и проверяй staged diff перед коммитом. Например, когда компонент сцены уже создан:

```sh
git add src/App.tsx src/game/GameCanvas.tsx
git diff --cached
git diff --cached --check
git commit -m "feat: add PixiJS game scene"
git push -u origin feat/01-game-scene
```

Если урок меняет другие файлы, добавь их явно. PR можно открыть через GitHub после push. Небольшие исправления review добавляем новыми коммитами в ту же ветке. Первый коммит не означает, что код больше нельзя исправлять.

## Что обсуждаем на review

- Выполнен ли критерий готовности и можно ли воспроизвести результат?
- Понятны ли имена, типы и границы ответственности?
- Удаляются ли canvas, ticker и обработчики при размонтировании?
- Что происходит при потере фокуса, повторном запуске и ошибке загрузки?
- Какие проверки действительно подтверждают поведение?
- Может ли автор объяснить одно ключевое решение и его ограничение?

Формат ответа ассистента: существенные замечания с файлом и причиной, затем краткое объяснение темы и следующий маленький шаг. Если замечаний нет, это тоже результат review.

## Коммиты

Сообщения — по-английски, одна понятная цель:

- `feat: add player movement`
- `fix: stop movement when the window loses focus`
- `test: cover landing on platform edges`
- `docs: explain the game loop`

`main` хранит проверенное состояние. GitHub Actions сейчас проверяет lint и сборку; тесты подключим к CI, когда появятся соответствующие механики. Публикация репозитория и публикация играбельного сайта — разные этапы.
